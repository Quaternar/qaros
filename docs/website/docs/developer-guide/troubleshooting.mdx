## Joining QAROS as a local app

What the user sees when a source app on the QAROS PC cannot join, and what fixes it. The [Vulkan cube](https://github.com/Quaternar/qaros/tree/main/qar-streaming-c/examples/vulkan_cube) prints each of these.

| Symptom | Cause | Fix |
|---|---|---|
| `qar_library_load(NULL)` returns `false` | no `qar-streaming-c.dll` beside the executable, `QAROS_RUNTIME_DIR` unset, no QAROS installation on this PC, and none on `PATH` | install QAROS ([Installation](/docs/operator-guide/installation)) |
| The app runs an older or newer runtime than the installed QAROS | a `qar-streaming-c.dll` beside the executable, or `QAROS_RUNTIME_DIR`, wins over the installation | remove the copy beside the app, or unset `QAROS_RUNTIME_DIR` |
| `QAR_STATUS_ONBOARDING_HUB_UNREACHABLE` (1802) | QAROS is installed but not running: no tray icon. The QAROS service waits up to a minute for a Hub to start before it answers so | start **QAROS** from the Start menu, then start the app again |
| `QAR_STATUS_ONBOARDING_APPROVAL_DENIED` (1805) | someone clicked **Deny** or closed the prompt, or an operator revoked the app | start the app again and click **Allow**. Nothing is remembered from a Deny. |
| `QAR_STATUS_ONBOARDING_APPROVAL_TIMEOUT` (1806) | nobody answered the prompt within 120 s | retry, and answer the prompt in the Visualizer or the QAROS tray window. Raise `approval_timeout_ms` if users need longer (at most 10 minutes). |
| `QAR_STATUS_ONBOARDING_HUB_NOT_AUTHENTIC` (1807) | the program serving the local enrollment pipe is not the installed, signed QAROS | do not retry. Reinstall QAROS from the official installer; if it persists, contact your administrator. |
| `QAR_STATUS_ONBOARDING_APP_IDENTITY_MISMATCH` (1808) | the executable was moved, copied, re-signed or modified since its approval, or its signature is invalid | revoke the old approval ([Approved local apps](/docs/operator-guide/source-applications#approved-local-apps)) and start the app again. An invalid signature can never be approved: re-sign or rebuild. |
| `QAR_STATUS_ONBOARDING_FAILED` (1801), message names a runtime version or flavor | the app loaded a `qar-streaming-c.dll` other than the installed one | load the installed runtime with `qar_library_load(NULL)`; do not ship a copy |
| asked again after every build | the app is not code-signed, so its approval is for one exact file | expected during development; sign release builds ([The trust record](/docs/developer-guide/onboarding-and-sessions#the-trust-record)) |
| `QAR_STATUS_ONBOARDING_INVITE_REFUSED` (1812) from `qar_session_request_onboarding_invite` | the session did not join as a local app (`QarOnboardLocalAppExt`) and was not started by QAROS: a code-paired app, a device or a co-process | final, do not retry; request the invite from the session of the local app that starts the co-process ([Co-process](/docs/developer-guide/onboarding-and-sessions#co-process-a-process-your-app-starts)) |
| the app stopped receiving after a hub reset, or after its approval was revoked | the session reached `QAR_SESSION_LIFECYCLE_STATE_RE_PAIR_REQUIRED` (C# `SessionLifecycleState.RePairRequired`): the hub no longer admits the app, and nothing is retried | subscribe to the session lifecycle; on `RE_PAIR_REQUIRED` destroy the session, onboard again and recreate what the app owns ([When the hub's session changes](/docs/developer-guide/onboarding-and-sessions#when-the-hubs-session-changes)) |
| frames pause for a few seconds and other peers' objects vanish briefly after the operator starts a new session | the session moves into the new session in place, and senders renegotiate | nothing: the app's own objects are kept. React only where the app keyed something by the session id ([When the hub's session changes](/docs/developer-guide/onboarding-and-sessions#when-the-hubs-session-changes)) |

## Choosing the GPU

| Symptom | Fix |
|---|---|
| the app renders on one GPU while the session uses another | create your graphics device on the session's adapter (`qar_session_get_graphics_device_id`), or chain the adapter you render on as `QarGraphicsDeviceId` ([Choosing the GPU](/docs/developer-guide/onboarding-and-sessions#choosing-the-gpu)) |
| `QAR_STATUS_ARGUMENT_NOT_SUPPORTED` from onboard with a `QarGraphicsDeviceId` | the adapter is not supported: only NVIDIA GPUs are |
| the Vulkan cube picks the wrong GPU | the cube renders on its session's GPU: the target's GPU when QAROS started it (launch invite or `QAR_GPU_ADAPTER_ID`, read by the library), otherwise the library's pick. The cube itself reads no environment variable, prints the GPU it uses and stops when no Vulkan device matches. |

## Status codes that are part of normal flow

| Status | Meaning | What to do |
|---|---|---|
| `QAR_STATUS_ONBOARDING_SESSION_NOT_FOUND` | The onboarding ID has no persisted slot on this machine | Fall back to `qar_runtime_onboard` — this is the expected first-run path |
| `QAR_STATUS_PAKE_ERROR` | Pairing code wrong or expired (codes live ~10 s) | Re-prompt the user for the current code and retry |
| `QAR_STATUS_ONBOARDING_HUB_UNREACHABLE` | Code onboarding could not reach a Hub | Verify the Hub is running, host/port (remote Hubs need a `QarOnboardHostExt`), and firewall/multicast on the network |
| `QAR_STATUS_ONBOARDING_SESSION_STILL_ACTIVE` | `forget` called while the session is active | Call `qar_session_handle_destroy` first, then `forget` |
| `QAR_STATUS_MEDIA_STREAMING_STREAM_IS_PAUSED` | The receiver paused the stream, for example because its display is not visible | Keep the sender and skip the frame; it resumes when the receiver does. Recreating the sender only restarts the negotiation |
| `QAR_STATUS_MEDIA_STREAMING_STREAM_IS_RECONNECTING` | The stream lost its peer and is reconnecting | Skip the frame and keep calling; a dead peer is noticed within ~2 s, a restarted one streams again within a few seconds |
| `QAR_STATUS_RENDERING_PRODUCER_APP_VOLUME_UNRESOLVED` | The sender's app volume does not resolve yet (or was closed), so there is no app content space to hand poses out in | Keep calling `begin_frame`; create the volume before the sender and recreate one you closed |
| `QAR_STATUS_RENDERING_PRODUCER_STREAM_IS_CLOSED` | The sender's stream was closed for good | Destroy the sender; create a new one if the target is still in the peer list |

## Checking results

Every fallible call reports success or failure the same way — inspect it rather than assuming success. The status code is what you branch on to tell a normal-flow condition (above) apart from a real error:

<CodeTabs>
<Lang value="c">

```c
QarRejoinInit rejoin = qar_rejoin_init_default();
rejoin.onboarding_id = onboarding_id;
QarResult r = qar_runtime_rejoin(runtime, &rejoin, NULL, NULL, NULL, &session);
if (qar_result_is_success(r))
{
    /* use session */
}
else if (qar_result_has_code(r, QAR_STATUS_ONBOARDING_SESSION_NOT_FOUND))
{
    /* expected first-run: fall back to qar_runtime_onboard */
}
else
{
    qar_result_log_if_error(r); /* log status code + message */
}
```

</Lang>
<Lang value="csharp">

```csharp
Result<Session> result = runtime.Rejoin(new RejoinOptions(onboardingId));
if (!result.IsSuccess)
{
    ResultInfo info = result.Info;
    if (info.StatusCode == StatusCode.OnboardingSessionNotFound)
    {
        // expected first-run: fall back to the binding's onboard flow
    }
    else
    {
        // log info.StatusCode and info.Message
    }
}

// Or, to turn any failure into a NativeCallException:
using Session session = result.ValueOrThrow();
```

</Lang>
</CodeTabs>

:::info
The C# snippet above is illustrative — it tracks the `Quaternar.Qaros` binding surface but
is not yet compiled from a published sample project.
:::

## Frequent integration mistakes

- **Forgetting to persist the onboarding ID** after code pairing. The ID returned by onboarding is the *only* key to the persisted identity. Losing it means pairing again. A local app and a co-process store nothing: their onboarding ID is zero.
- **Calling API functions from inside callbacks.** Result/progress/update callbacks run on library threads; blocking API calls from there can deadlock. Queue to your own thread.
- **Zero-initializing init structs by hand.** Always use `qar_*_default()` — it stamps `header.type`, without which calls fail.
- **Mismatched projection metadata.** If streamed content "swims" or sits at the wrong depth, your `show_frame` near/far or per-view poses don't match what you actually rendered with. This is a metadata bug, not a network problem — see [Rendering Streams](/docs/developer-guide/rendering-streams#the-frame-loop).
- **Confusing panel and volume pose conventions.** Panel pose = midpoint of the top edge; volume pose = cuboid center.
- **A depth format the sender cannot take.** `qar_render_sender_create` fails with `QAR_STATUS_RENDERING_PRODUCER_DEPTH_FORMAT_NOT_SUPPORTED` when the graphics API refuses the format (D24S8 and D32S8 on CPU and D3D11) or the GPU cannot create it. Use `QAR_PIXEL_FORMAT_D32_FLOAT`, which works everywhere — see [Choosing a depth format](/docs/developer-guide/rendering-streams#choosing-a-depth-format).
- **Destroying the runtime while async operations run.** Cancel (and wait for the exactly-once result callback) before teardown.

## Where to look

- **Library logs** — enable with `QarLibraryInit.enable_console_logging` and/or `log_folder_path`.
- **Hub-side logs** — the QAROS Hub log folder on the Hub machine.
- **Warping monitor** — the visualizer's timing view shows per-volume stream latency/FPS/jitter, which quickly separates "my app renders slowly" from "the network is dropping frames".

## Crash dumps

If your process crashes while the C API is loaded, it writes `<time>_<process>_<pid>.crash.txt` and a `.dmp` into `crashes/` under the `log_folder_path` you passed to `qar_library_init` (otherwise `%TEMP%\quaternar\crashes`). Hub processes write theirs next to their logs (see [Running the Hub](/docs/operator-guide/running-the-hub#crash-dumps)). Attach both files and the logs beside them to a bug report.

For a GPU crash or device loss, set `QAR_VULKAN_CRASH_DIAGNOSTIC=1` before starting the processes. With the Vulkan SDK's crash diagnostic layer installed, QAROS loads it and it names the command the GPU was executing (output folder: the layer's `CDL_OUTPUT_PATH`); without the layer the variable does nothing. It is off by default because it records every command buffer.

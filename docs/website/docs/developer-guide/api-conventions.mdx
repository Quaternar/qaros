# API Conventions

<LanguageSwitcher />

The API is deliberately uniform: once you know these six patterns, every module
(onboarding, panels, volumes, streams, peers) reads the same way. The concepts
are identical across languages; the idioms differ. Pick your language above.

## 1. Opaque handles and value IDs

Two kinds of identifiers exist everywhere. **Opaque handles** are references to
library-owned objects — you never inspect them, you pass them back to the API and
release them. **Value IDs** are small copyable UUID values you can store,
compare, stringify, and persist.

The key rule: **releasing a handle is not the same as destroying the thing it
refers to.** Tearing down your reference to a session keeps your persisted
identity intact (so you can rejoin silently next time); actually erasing that
identity is a separate, explicit call.

<CodeTabs>
<Lang value="c">

- **Opaque handles**: `QarRuntime*`, `QarSession*`, `QarGuiPanel*`,
  `QarAppVolume*`, `QarPeerSpec*`, `QarCancelToken*`, `QarOnboardingInvite*`.
  Release with the matching `qar_*_handle_destroy()`.
- **Value IDs**: `QarPeerId`, `QarSessionId`, `QarGuiPanelId`, `QarAppVolumeId`,
  `QarStreamId`, `QarOnboardingId`. Compare with `qar_*_id_equals`, render with
  `qar_uuid_to_string`.

```c
// Releasing the handle tears down the live session but KEEPS the identity:
qar_session_handle_destroy(session);

// Erasing the persisted identity is a separate, explicit call on the runtime:
QarForgetInit forget = qar_forget_init_default();
forget.onboarding_id = saved_id;
qar_result_log_if_error(qar_runtime_forget(runtime, &forget));
```

</Lang>
<Lang value="csharp">

- **Opaque handles** are `SafeHandle`-backed classes implementing `IDisposable`:
  `Runtime`, `Session`, `OnboardingInvite`, `RenderSender`, `RenderFrameInfo`.
  `Dispose()` (or a `using` block) releases the handle. `Runtime.Dispose()` calls
  `qar_runtime_handle_destroy`: it releases this process's runtime handle; the
  Hub and the other applications in its session keep running.
- **Value IDs** are `readonly struct`s — `PeerId`, `SessionId`, `GuiPanelId`,
  `AppVolumeId`, `StreamId` — with `ToString()`, `Parse`/`TryParse`,
  `ToByteArray()`, and equality **by byte content**. (`PeerId`, `SessionId`, and
  `GuiPanelId` also expose a static `Unique()`.)

```csharp
// Disposing the Session tears down the live session but KEEPS the identity:
session.Dispose();

// Erasing the persisted identity is a separate call on the runtime:
runtime.Forget(new ForgetOptions(savedOnboardingId)).EnsureSuccess();

// IDs compare by value:
if (a == b) { /* same peer */ }
```

</Lang>
<Lang value="rust">

{/* Generated by cargo xtask guide from examples/guide/api-conventions.md of the Rust binding. Edit that file, not this tab. */}

- **Handles** are owned values that release their C handle on drop: `Library`, `Runtime`, `Session`, `RenderSender`, `CancelToken`, `OnboardingInvite`. Each keeps its parent alive, so the C teardown order holds.
- **Value IDs** are `Copy` newtypes over the 16 UUID bytes: `PeerId`, `SessionId`, `GuiPanelId`, `AppVolumeId`, `StreamId`, `OnboardingId`. They compare with `==`, and `library.uuid_to_string` renders one for persisting.

```rust
// Dropping the Session tears down the live session but KEEPS the identity:
drop(session);

// Erasing the persisted identity is a separate, explicit call on the runtime:
runtime.forget(saved_id)?;

// IDs are Copy values that compare by their bytes; the library renders them as text:
let same_peer = first_peer == second_peer;
let saved_text = library.uuid_to_string(&saved_id.0)?;
```

</Lang>
</CodeTabs>

## 2. Results and status

Every fallible call reports success or failure by value — never by throwing for
an *expected* native condition. Some status codes are **expected control flow**,
not errors: a rejoin that reports "session not found" means "onboard instead",
and a pairing error means "re-prompt the user for the code".

<CodeTabs>
<Lang value="c">

Every fallible function returns a **`QarResult` by value**:

```c
QarResult r = qar_some_call(...);
if (qar_result_is_error(r)) { /* handle */ }
if (qar_result_has_code(r, QAR_STATUS_ONBOARDING_SESSION_NOT_FOUND)) { /* onboard */ }
qar_result_log_if_error(r);   // convenience: log if it was an error
```

`qar_result_is_success` / `qar_result_is_error` test the outcome;
`qar_result_has_code` matches a specific `QarStatusCode`.

</Lang>
<Lang value="csharp">

Fallible calls return **`Result<T>`** (or `Result<Unit>` for void-like
operations). No exception is thrown for a native failure — you inspect the
result:

```csharp
Result<Session> r = runtime.Rejoin(rejoinOptions);
if (!r.IsSuccess)
{
    ResultInfo info = r.Info;           // info.StatusCode, info.Message
    if (info.StatusCode == StatusCode.OnboardingSessionNotFound) { /* onboard */ }
}

// Or take the value, throwing NativeCallException on failure:
using var session = r.ValueOrThrow();

// Or assert success on a void-like call:
runtime.Forget(new ForgetOptions(savedOnboardingId)).EnsureSuccess();
```

</Lang>
<Lang value="rust">

{/* Generated by cargo xtask guide from examples/guide/api-conventions.md of the Rust binding. Edit that file, not this tab. */}

Every fallible call returns **`qaros::Result`**. A C failure is `Error::Api`, which keeps the C function's name, the `StatusCode` and the text of `qar_result_message`; `?` propagates it.

```rust
let session = match runtime.rejoin(saved_id, presentation, &BlockingOptions::default()) {
    Ok(session) => Some(session),
    // Expected control flow, not an error: no persisted slot, so onboard instead.
    Err(error) if error.has_code(StatusCode::ONBOARDING_SESSION_NOT_FOUND) => None,
    // Anything else: the error names the C function, the status code and the message.
    Err(error) => return Err(error),
};
```

`error.has_code` matches the status code. `error.has_cause` also sees the causes that begin-frame wraps inside `RENDERING_UNABLE_TO_BEGIN_FRAME`, as `qar_result_has_code` does in C.

</Lang>
</CodeTabs>

## 3. Extensible init structs (`QarStructureHeader`)

Optional capabilities are added by **chaining extension structures** onto a base
init struct — the same pattern OpenXR and Vulkan use. This is how the API grows
without ever changing a signature: new capabilities appear as new extension
structs. For example, onboarding targets the local Hub by default; an extension
redirects it to a remote host.

<CodeTabs>
<Lang value="c">

Every `...Init` struct begins with a `QarStructureHeader { type, next }`. Always
build it with its `qar_*_default()` helper (which zero-fills and stamps `type`),
then chain extensions through `next`:

```c
QarOnboardInit init = qar_onboard_init_default();
QarOnboardCodeExt code = qar_onboard_code_ext_default();
QarOnboardHostExt host = qar_onboard_host_ext_default();

code.code = code_from_user;        // read from the user, never a command line
host.hostname = "192.168.1.50";
host.port = hub_port;              // required: shown with the hub's code
code.header.next = &host.header;   // chain code -> host
init.header.next = &code.header;   // chain init -> code
```

</Lang>
<Lang value="csharp">

Extensions are modelled as managed `Structure` descriptors (each with a
`StructureType`), but normal C# callers do not wire native chains directly.
Instead, options objects expose fluent builder methods such as
`WithExtension(...)`, `WithHost(...)`, or `WithViewOverrides(...)`. The binding
marshals the resulting chain into the native `next` pointers and frees the
unmanaged memory afterwards:

```csharp
var options = new OnboardOptions()
    .UseCode(codeFromUser)
    .WithHost("192.168.1.50", hubPort); // the port is required
```

</Lang>
<Lang value="rust">

{/* Generated by cargo xtask guide from examples/guide/api-conventions.md of the Rust binding. Edit that file, not this tab. */}

The safe API builds the init structs, stamps them with ports of the `qar_*_default()` helpers and chains the extensions. You pass Rust values: an enum for the onboarding mode, an `Option` for an optional extension such as the hub address. For raw calls through `library.raw_api()`, `qaros_sys::defaults` has the same helpers.

```rust
// The code and host extensions, chained and stamped by the binding:
let method = OnboardMethod::Code {
    code: "ABCD-EFGH",
    hub: Some(HubAddress {
        hostname: "192.168.1.50",
        port: hub_port, // shown with the hub's code
    }),
};
let onboarded = runtime.onboard(&method, presentation, &BlockingOptions::default())?;
```

</Lang>
</CodeTabs>

## 4. Blocking / async pairs

Every long-running operation exists twice: a **blocking** form and an **async**
form. The blocking form can report progress while you wait; the async form
returns immediately and delivers its outcome later, exactly once, including on
cancellation.

<CodeTabs>
<Lang value="c">

- **Blocking**: `qar_runtime_onboard(...)` blocks until done; an
  optional *progress callback* fires from an internal thread while you wait.
- **Async**: `qar_runtime_onboard_async(...)` returns immediately; a
  *result callback* fires **exactly once** on a background thread — on success,
  error, *and* cancellation. After it returns, the library never touches your
  `user_state` again.

Both accept an optional **`QarCancelToken`** (`qar_cancel_token_create` /
`_with_timeout`), which you may cancel from any thread and must keep alive until
the operation finishes. Progress callbacks share one signature delivering a
severity, a percentage, and a message.

</Lang>
<Lang value="csharp">

- **Blocking**: synchronous methods return `Result<T>`.
- **Async**: `...Async` variants return `Task<Result<T>>` and accept a
  `System.Threading.CancellationToken`, which bridges to the native cancel token.

The distinction that trips people up: a **native failure completes the Task
successfully** with a `Result` whose `IsSuccess` is `false` (the task itself is
not faulted); only **managed cancellation** produces a canceled task.

```csharp
CancellationToken ct = /* your token */;
Result<Session> r = await runtime.RejoinAsync(rejoinOptions, cancellationToken: ct);
if (!r.IsSuccess) { /* native failure — inspect r.Info */ }
```

</Lang>
<Lang value="rust">

{/* Generated by cargo xtask guide from examples/guide/api-conventions.md of the Rust binding. Edit that file, not this tab. */}

- **Blocking**: `Runtime::onboard`, `Runtime::rejoin` and `Session::create_render_sender` block until done. Their `BlockingOptions` take an optional progress channel, fed from a library thread while you wait, and an optional `CancelToken` (`library.create_cancel_token`, with or without a timeout), which the borrow keeps alive for the call. Its `cancel_handle()` cancels it from another thread.
- **Async**: `Runtime::start_onboard` and `Runtime::start_rejoin` return a `PendingOnboard`, `Session::start_render_sender` a `PendingRenderSender`, at once; `poll()` hands over the outcome once the library called back (`PendingOnboard::wait` blocks for it). The library calls back exactly once, with `StatusCode::TIMEOUT` when the call is cancelled; dropping the pending value cancels it. `RenderSender::start_owned_frame` is the async begin-frame (`PendingFrame`).

```rust
let token = library.create_cancel_token(Some(Duration::from_secs(120)))?;
let (progress, reports) = mpsc::channel();
let onboarded = runtime.onboard(
    &OnboardMethod::LocalApp {
        approval_timeout: None,
        app_tag: None,
    },
    &PeerPresentation::default(),
    &BlockingOptions {
        progress: Some(progress), // reports sent from a library thread while the call blocks
        cancel: Some(&token),     // borrowed, so it outlives the call
    },
)?;
for report in reports.try_iter() {
    println!("{:.0}% {}", report.percent, report.message);
}
```

```rust
// Returns at once; the creation is cancelled after 10 s.
let mut pending = session.start_render_sender(config, Some(Duration::from_secs(10)), || {})?;

// On each frame of your loop: None while the library creates the sender,
// then the sender or the error the library delivered.
let created: Option<RenderSender> = pending.poll().transpose()?;
```

</Lang>
</CodeTabs>

:::warning Callback threading
Result and progress callbacks (in C) and subscription/event callbacks (in every
language) arrive on **library threads**. Do not call blocking QAROS functions
from inside them, and marshal to your own thread before touching single-threaded
application state.
:::

:::info Ending a subscription
When `qar_cancel_token_cancel`, `qar_cancel_token_handle_destroy`,
`qar_session_handle_destroy` or `qar_library_destroy` returns (in C#, `Dispose`
of the subscription; in Rust, dropping its `Subscription`, which cancels its
token), a callback of the subscription that was running on another thread has
finished, and none starts afterwards. Free `user_state` right after that call.
Called from inside the subscription's own callback, these calls return without
waiting for it. Never end a subscription while holding a lock its callback
takes.
:::

## 5. Enumeration and string getters

Reading a variable-size collection or string is a snapshot operation in every
language: the shape of the call differs, the meaning does not.

<CodeTabs>
<Lang value="c">

Enumerations use the two-call **count-then-fetch** idiom; string getters take a
caller-provided buffer plus size; serialization uses `*_serialized_size` then
`*_serialize`:

```c
size_t count = 0;
qar_query_peer_specs_count(session, &count);          // 1: ask for the size
QarPeerSpec** specs = malloc(count * sizeof(*specs));
qar_query_peer_specs(session, specs, count, &count);  // 2: fetch
// ... use ...
for (size_t i = 0; i < count; ++i) qar_peer_spec_handle_destroy(specs[i]);
free(specs);
```

</Lang>
<Lang value="csharp">

Enumerations return an immutable snapshot as `Result<T[]>`; strings return
`Result<string>`. On `net8.0` there is also an `IAsyncEnumerable<T>` for live
updates, and on `netstandard2.1`/`net8.0` the ID types offer `Span<byte>`
overloads.

```csharp
Result<PeerSpec[]> peers = session.Peers.GetAll();
foreach (PeerSpec p in peers.ValueOrThrow())
{
    // p is an immutable snapshot — safe to keep
}
```

</Lang>
<Lang value="rust">

{/* Generated by cargo xtask guide from examples/guide/api-conventions.md of the Rust binding. Edit that file, not this tab. */}

Enumerations return an owned snapshot, a `Vec` of plain Rust values: the binding runs the count-then-fetch and releases every handle it fetched. String getters return `String`.

```rust
for peer in session.peers()? {
    // peer is a PeerInfo snapshot: owned, safe to keep
    println!("{} {}", peer.display_name, peer.app_version);
}
```

</Lang>
</CodeTabs>

## 6. Ownership and lifetime

The lifetime discipline is the same idea in every language: you own what you
receive, borrowed things handed to you inside a callback are valid only for that
callback, and teardown runs in reverse of setup.

<CodeTabs>
<Lang value="c">

- Init structs and the strings they point to are **copied before the call
  returns** — stack-allocate freely.
- Out-handles are **owned by you**: release every handle you receive (from calls
  *and* from result callbacks) with its `*_handle_destroy`.
- Handles delivered *inside* a callback are **borrowed** — read what you need
  during the callback; do not store the handle.
- A session handle keeps the runtime alive internally, so destruction-order
  mistakes don't dangle — but the intended order is: destroy session handle →
  destroy runtime → destroy library.
- The API is designed for **single-threaded use** per runtime; callbacks are the
  only cross-thread surface.

</Lang>
<Lang value="csharp">

- Every handle type is `IDisposable` — use `using`, or dispose explicitly. The
  underlying `SafeHandle.ReleaseHandle` calls the matching native handle release.
  In particular, `Runtime.Dispose()` releases only this process's runtime handle;
  the Hub outlives your app.
- **Subscriptions are `IDisposable`**: disposing one stops native delivery.
- Values handed to you inside an event/callback are already **immutable DTO
  snapshots** (`PeerSpec`, `GuiPanel`, `AppVolume`) — safe to keep; there is no
  borrowed native handle to worry about.
- `Dispose` of a `Session`, a sender, a `RenderFrameInfo` or the `Runtime` is
  safe while another thread is inside a call on it: new calls throw
  `ObjectDisposedException` at once, calls that wait (a `BeginFrame` through a
  paused stream, a hub request) are cancelled and fail, and `Dispose` waits until
  the running calls returned (async ones until their completion fired). Then it
  releases the native object on the calling thread, so a graphics sender is
  released where you dispose it, and a session's subscriptions have ended when
  `Dispose` returns. Do not dispose from a QAROS callback or event handler: from
  one of the object's own callbacks, or while another thread is in a call on the
  object, `Dispose` throws `InvalidOperationException` there instead of waiting
  on the library thread.
- `ObjectDisposedException` is thrown only for **managed misuse** (using an
  object after you disposed it), never for native failures.
- Dispose in reverse: session, then runtime, then `Library.Destroy()`.

</Lang>
<Lang value="rust">

{/* Generated by cargo xtask guide from examples/guide/api-conventions.md of the Rust binding. Edit that file, not this tab. */}

- Every handle is released on drop and keeps its parent alive (render sender, session, runtime, library), so teardown runs in the documented order whatever order your values drop in.
- Callbacks receive owned snapshots (`PeerInfo`, `AppVolumeInfo`, `GuiPanelInfo`, `RenderRequest`), never a borrowed C handle: keep them as long as you like.
- A subscription returns a `Subscription` guard: dropping it stops delivery, and `detach()` keeps it until the session ends.
- Handles are not `Send`: use a runtime from one thread; callbacks are the only cross-thread surface. A `CancelToken` is cancelled from another thread through its `cancel_handle()`.
- One `Library` per process: a second load is refused while one lives, and the runtime stays loaded until the process exits.

</Lang>
</CodeTabs>

# QAROS Changelog

Everything that changes what QAROS users build against or see: the C API and C# API (SDK), the
Unity packages, the visualizer, what the mixer renders, the device apps, and changed assumptions
such as coordinate systems, units, colours and defaults. Each entry names the surface it
applies to. **Breaking** lists what needs action on your side when updating.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and versions follow
[Semantic Versioning](https://semver.org/spec/v2.0.0.html). In 0.x a minor version is a feature
upgrade that tries hard not to break you; when it must, the change is under **Breaking** with the
step to take. Only the latest version is supported.

This file is generated by `packaging/changelog.py publish` in the Quaternar repository for every
release candidate and release. Only `Docs` entries (changes to this repository's documentation)
are written here by hand, under `Unreleased`; every other entry is overwritten.

## [Unreleased]

First versioned release. Everything below is the baseline later entries are measured against.

### Breaking

- **Runtime:** the hub's onboarding listener (discovery requests, pairing, shared-password
  onboarding) no longer uses TCP `7445`. Each hub takes the first free port of its router range
  (`routerPortRangeStart`-`routerPortRangeEnd`, default 19120-19199), bound exclusively, so two hubs
  on one PC no longer share it. Open the hub range in the firewall (TCP+UDP 19120-19200); a rule
  for TCP `7445` alone no longer lets devices pair. `discoveryPort` now defaults to `0`; set it (or
  `onboardingPakePort`) only to pin the port, and the hub then fails to start if that port is
  taken. The UDP multicast beacon stays on `239.77.77.77:7445`.
- **Runtime:** a QAROS API app the launcher starts reads a full onboarding invite as its first
  stdin line: one line of JSON with the hub's IP, onboarding port, a one-time code and the CA
  fingerprint, instead of a bare code. Pass it to `qar_onboarding_invite_deserialize` and onboard
  with `QarOnboardInviteExt`; a line that does not start with `{` is still a typed code.
- **Visualizer:** pairing with another hub by address needs `host:port` (the port is shown with
  that hub's code); a host alone is not accepted. The "reach this machine at" rows of the
  onboarding window show `host:port`.
- **Device apps:** the HoloLens 2 player's package version follows the product version
  (`0.9.0.x`). A HoloLens with an earlier player build (`1.0.0.0`) must uninstall it before
  installing this one.
- **Unity:** the package connects through hub onboarding. Fill
  `QarMultiUserStreamingBehaviour > Onboarding > Code` with the pairing code from the hub's
  onboarding screen (`Hub Host` for a remote hub) before the first connect; the onboarding id is
  then saved in `PlayerPrefs` and later connects rejoin without a code. `ForgetOnboarding()`
  unpairs. All endpoints share one session.
- **Unity:** endpoint connection targets changed. `visualizer` now uses a visualizer already on
  this machine's hub (`visualizer:N` picks another) instead of launching one per endpoint;
  `hololens:<host>`, `quest:<host>`, `android:<host>` or a bare HoloLens host ask the local hub to
  start the device's target app, which is stopped again on disconnect. `zed`, a bare `quest` and
  JSON connection strings are no longer accepted.
- **Unity:** each endpoint's app volume is kept by its new `AppVolumeCommonName` (default
  `<product name>/<endpoint name>`): reconnecting gets the same volume and placement back, and a
  disconnect no longer removes it.
- **C API:** `QarHand` is gone; `QarHandedness` names both the hand of a gesture and the axis
  handedness of a `QarGeoAnchorFrame`, renumbered `QAR_HANDEDNESS_UNSPECIFIED = 0`,
  `QAR_HANDEDNESS_LEFT = 1`, `QAR_HANDEDNESS_RIGHT = 2` (`RIGHT` was 0).
  `qar_gui_panel_gesture_get_hand` is now `qar_gui_panel_gesture_get_handedness`, and
  `qar_app_volume_gesture_get_hand(gesture, out_hand, out_has_hand)` is now
  `qar_app_volume_gesture_get_handedness(gesture, out_handedness)`: a two-hand gesture reports
  `UNSPECIFIED` instead of a `has_hand` flag. `qar_app_volumes_get_or_create` (with
  `has_app_world_anchor`) and `qar_app_volumes_change_app_world_anchor` reject an `UNSPECIFIED`
  frame with `QAR_STATUS_ARGUMENT_NOT_SUPPORTED`; a zero-initialized frame used to mean
  right-handed, so set `handedness` explicitly. An app volume without an anchor reads back
  `UNSPECIFIED`.
- **SDK:** app world anchors are stored in a new schema version. A peer of an earlier build reads
  the handedness of an anchor written by this version swapped; run every peer of a session on
  the same version.
- **C#:** the API is `Quaternar.Qaros`: namespace (was `Qar`), assembly `Quaternar.Qaros.dll` (was
  `QarStreamingSharp.dll`) and NuGet. `Vector3`, `Vector3d`, `Quaternion` and `Pose` moved to
  `Quaternar.Qaros.Mathematics`, so they no longer clash with `UnityEngine` or `System.Numerics`.
  Replace `using Qar;` with `using Quaternar.Qaros;` and add `using Quaternar.Qaros.Mathematics;`
  where you use poses or vectors.
- **C#:** `Hand` is gone; `Handedness` (`Unspecified = 0`, `Left = 1`, `Right = 2`) names both the
  hand of a gesture and the axis handedness of a `GeoAnchorFrame`. `AppVolumeGestureEvent.Hand` and
  `GuiPanelGestureEvent.Hand` are now `.Handedness`; `AppVolumeGestureEvent.HasHand` is removed, a
  two-hand gesture reports `Handedness.Unspecified`. `Handedness.Right` was 0: a default
  `GeoAnchorFrame` is now `Unspecified` and rejected with `ArgumentNotSupported`; set it
  explicitly.
- **C API:** ending a subscription now waits for its callbacks. When `qar_cancel_token_cancel`,
  `qar_cancel_token_handle_destroy`, `qar_session_handle_destroy` or `qar_library_destroy`
  returns, a callback of the subscriptions it ends that was running on another thread has
  finished and none starts afterwards, so `user_state` may be freed right after the call. Called
  from inside that subscription's own callback, cancel and destroy return without waiting for it.
  Do not end a subscription while holding a lock its callback takes, or the call deadlocks; a
  token timeout still does not wait. GUI panel gesture subscriptions get the same guarantee from
  their token; one started with a `NULL` token ends with its session.
- **C#:** disposing a subscription returned by a `Subscribe*` method waits for a handler call
  running on another thread and no handler runs after `Dispose` returns; disposing from inside the
  handler returns at once. Do not dispose while holding a lock the handler takes.
- **SDK:** a common name must be ASCII. `qar_app_volumes_get_or_create` /
  `qar_gui_panels_get_or_create` (and `GetOrCreateRoom`) reject one with any other character;
  display names stay free UTF-8, emoji included.
- **SDK:** hubs have no fixed onboarding port any more; each claims one from its port range. Code
  onboarding without `QarOnboardHostExt` (C# without `WithHost`) finds the hub of the same user:
  first through `hub-endpoint.json` in the QAROS data root, then through a discovery beacon whose
  owner is this user on this PC (up to 6 s), else it fails with
  `QAR_STATUS_ONBOARDING_HUB_UNREACHABLE` asking for host:port. It no longer dials
  `127.0.0.1:7445`.
- **C API:** `QarOnboardHostExt.port` is required; `0` is rejected with
  `QAR_STATUS_ARGUMENT_NOT_SUPPORTED`. Pass the port shown with the hub's onboarding code.
- **C#:** `OnboardOptions.WithHost(hostname, port)` and `OnboardHost(hostname, port)` take a
  required port; add the hub's onboarding port to calls that passed only the host.
- **SDK:** a QAROS API app started by QAROS gets a full invite as its first stdin line (one line
  of JSON starting with `{`), not a code. Deserialize it with `qar_onboarding_invite_deserialize`
  (C# `OnboardingInvite.Deserialize`) and onboard with `QarOnboardInviteExt`; treat any other line
  as a typed code.
- **C API:** `qar_render_sender_last_hands` now returns each joint `radius` and both
  `joint_velocities` in app content space, like the poses: the radius and the linear velocity are
  divided by the app scale and both velocities are rotated into the app's axes. Drop any conversion
  your app applied to treat them as room metres and room axes.
- **SDK:** everything a render sender hands its app is in the bound app volume's app content
  space: view poses, the rendered pose given back, hand aim poses, joints, radii and velocities.
  Data read through data streams and shared objects stays in the publishing peer's room space. A
  render sender whose app volume does not resolve (not yet known to the session, or closed) no
  longer falls back to room space: begin-frame fails with the new
  `QAR_STATUS_RENDERING_PRODUCER_APP_VOLUME_UNRESOLVED` (C# `StatusCode.RenderingProducerAppVolumeUnresolved`,
  805) and `qar_render_sender_last_hands` reports both hands untracked. Treat the code as
  recoverable and keep calling begin-frame; recreate a volume you closed.
- **C#:** the bindings follow the v0 C API. `AppVolumeControl.Add` and `GuiPanelControl.Add` are
  `GetOrCreate`, and `AppVolumeOptions` / `GuiPanelOptions` take the required common name in their
  constructor instead of an optional `Id`. `AppVolumeGestureEvent` carries `Hand`, `GestureId` and
  `ModeId`. The unused legacy `QarNativeMethods` / `QarStructs` P/Invoke files are removed.
- **SDK:** a target that pauses (for example, its display is not visible) now pauses your render
  sender's stream instead of closing it. The sender, its stream and its app volume stay up.
  `qar_render_sender_begin_frame` and `_begin_frame_async` wait through the pause and begin the
  frame once the target resumes; `qar_render_sender_try_begin_frame` keeps `out_ready = false`.
  Before, begin-frame failed with a closed stream and apps recreated their senders. Keep the
  sender while it waits and drop any sleep-and-retry loop on a paused begin-frame; a render
  thread that must keep running cancels the wait with its `QarCancelToken` or polls
  `try_begin_frame`.

### Added

- **Runtime:** when the Hub cannot start, or a part of it keeps crashing (10 restarts within 10
  minutes), the tray shows a QAROS Hub window with copyable details instead of the splash just
  closing. Any crash of a Hub process also raises a tray notification that opens it, including a
  crash that ends the process before it can write a dump (a fail-fast or heap corruption): the
  launcher, or the tray for the launcher, then writes the crash report from the exit status.
  - **Create crash report** saves one ZIP of the Hub's recent logs and crash dumps (no keys or
    certificates) to Downloads, for you to send to Quaternar support. It is also in the tray menu.
    It includes the launcher runs before a restart and the newest three Windows Error Reporting
    dumps of QAROS programs (`%LOCALAPPDATA%\CrashDumps`, where configured). Its `report.txt` opens
    with the right characters in every Windows viewer.
  - **Clean data and start fresh** deletes the Hub's data on this PC (paired devices,
    certificates, sessions, settings; logs are kept) and starts it again.
- **Unity:** `QarDeviceBehaviour.ToUnityPosition`, `ToUnityRotation`, `ToUnityLinearVelocity`
  and `ToUnityAngularVelocity` convert render-sender data (OpenXR right-handed app content space)
  into Unity's left-handed space. `LeftHandJoints` / `RightHandJoints` stay raw app content space;
  convert with these, and never re-apply the app volume's pose or scale.
- **Visualizer:** Source Applications is one grid of app tiles with logos: built-in apps (StereoKit;
  CPU Renderer and Test OpenXR in debug mode), apps detected on this PC (the bundled Vulkan cube
  example, developer mode), and saved presets. Clicking a tile opens a modal to launch it, save it
  as a new preset, or edit and remove a preset. "+ Add source app" adds an OpenXR app, or from
  developer mode a QAROS API app, so you can test your own app without the debug password; name and
  logo come from the executable. A Running list shows status, uptime, Stop,
  live settings, and Streams to: all target applications or a selection of connected ones, changed
  without restarting the app. Bundled Test OpenXR starts Monado per target.
- **Runtime:** the launcher starts QAROS API apps (C or C# API) as one process for all targets. The
  app gets a one-time launch invite of its own on stdin (hub address, onboarding port, code), never
  its command line or a log, valid 2 minutes for that start only; the code on the hub's onboarding screen does not change when an
  app starts. The invite also names the target's GPU; the app reads no environment variable.
- **Packaging:** the runtime bundles `qar-vulkan-source`, the C SDK's Vulkan cube example, beside
  the launcher. It renders on the GPU its launch invite names, when it names one. Its optional hub
  argument is `host:port`.
- **Visualizer:** discovered hubs run by your own user account on this PC are listed first and
  marked `(yours)`.
- **Runtime:** the hub writes `hub-endpoint.json` (hub id, onboarding and router port) into its
  data root while it runs, so local apps given only a code find it.
- **Runtime:** Monado driver supports Linux GPU UUID selection and per-runtime IPC paths.
  Linux frame delivery still requires GPU-memory descriptor transport; Linux runtime validation
  remains outstanding.
- **Packaging:** Windows x64 runtime as `QAROS <version>.zip` (release) and
  `QAROS Demo <version>.zip` (demo): `qar-runtime-launcher`, the device applications and the C API
  under `bin/`, the C API header under `include/`.
- **Packaging:** C# NuGet packages `Quaternar.Qaros` and `Quaternar.Qaros.Demo`; they copy
  the native runtime next to the application on build and publish.
- **Unity:** packages `com.quaternar.streaming` and `com.quaternar.streaming.mrtk` as
  `QAROS Unity <version>.zip` and `QAROS Unity Demo <version>.zip`, installed with "Add package
  from disk", runtime included.
- **Packaging:** `CHANGELOG.md`, `third_party_licenses.md` and `README-Licensing.md` (LGPL notice)
  in every package.
- **Packaging:** every runtime ZIP and Unity ZIP carries `devices/`: the Vulkan player APKs for
  Meta Quest (`QAROS Player Quest`) and METALENSE 2 (`QAROS Player MetaLens`), the HoloLens 2 player
  package with its certificate and dependencies, and `devices/README.md` on installing each.
- **Device apps:** the Android app reports the product version as its version name, and its
  version code rises with every release candidate and release.
- **Visualizer:** the Stream Graph panel follows the UI mode.
  - **All modes:** a "This PC watches" strip shows each of this visualizer's receivers as a card
    with all of its controls on it: the name to rename it, state and fps, play/pause, stop and
    show buttons (hover for what each does) and an X in the corner to remove it. The dashed "Add
    receiver" card adds a receiver and starts it; its Texture Grid opens behind the tab you are on
    and its tab flashes for a few seconds instead of taking you there. Click the tab to watch it.
- **Visualizer:** every Texture Grid has an X that closes it. Closing it leaves its receiver
  running; a stream you watch from the Stream Graph stops when you close its last grid.
  - **Basic:** one card per target app (source apps -> mixer -> target), with its status, delay
    (Good / OK / High), fps, and a Watch button on every stream. A camera blended into a target
    shows as a source "blended at target"; video inside GUI panels is left out.
  - **Developer:** a graph with sources, mixers and targets as columns and machines as lanes.
    Each arrow shows its latency as measured by its receiver. Click an arrow, stream or app for a
    popup with Latency (mean, min - max, std dev, pose age), Jitter and FPS charts, with Watch /
    Stop watching at the top. Chips show latency and fps; drag a popup's edge to resize it.
  - A source app that feeds target apps directly sits right of them, so its arrows do not cross
    the mixer's.
  - The latency split shows the source app's render time, and how long the source app holds each
    frame and waits for the render request. Hover a part for what it measures. Pin popups to
    compare routes. Pan and Zoom toggles: drag or scroll to move, Ctrl + wheel to zoom, Fit and 1:1
    to reset. Streams into GUI panels are tagged.
  - **Debug:** also marks each receiver as primary, secondary or watching, and shows peer and
    stream ids and a per-stage latency breakdown.
  - The "Video Stream" panel is gone; its receivers and streams live in the Stream Graph.
- **Mixer:** warp feather for Warping mode. The trail a head movement drags beside a near object
  fades out instead of staying opaque, showing what is behind it; a trail more than half faded no
  longer stops a hand ray or hides the rays and wireframes behind it. On by default: turn it off
  with `"warpFeather": false` in the mixer config or `QAR_WARP_FEATHER=0`. Tune where the fade
  starts and ends with `warpFeatherStartMagnification` / `QAR_WARP_FEATHER_START` (default 2) and
  `warpFeatherEndMagnification` / `QAR_WARP_FEATHER_END` (default 6). Legacy mode is unaffected.
- **Mixer:** optional source alpha. With `"mixerSourceAlpha": true` in the mixer config or
  `QAR_MIXER_SOURCE_ALPHA=1`, each source application's alpha is composited instead of drawn
  opaque: translucent surfaces that write depth, soft edges, and one app volume seen through
  another. The application's colour must be premultiplied by its alpha (rendered over a
  transparent-black clear, as the Unity package's cameras are) and its alpha channel kept correct
  through post-processing. Transparent materials that write no depth still do not appear. Off by
  default, because an application whose alpha channel is undefined would turn invisible.
- **C#:** XML documentation for the public `Quaternar.Qaros` API: units, coordinate spaces, threading and
  lifetime rules, and the status codes to handle. Shows in IntelliSense (the NuGet ships
  `Quaternar.Qaros.xml`) and in the C# API reference on the documentation site.
- **C API:** `QAR_STATUS_MEDIA_STREAMING_STREAM_IS_PAUSED` (C#
  `QarStatusCode.MediaStreamingStreamIsPaused`): a frame call on a stream its receiver paused,
  for example because its display is not visible. Keep the sender; it resumes when the receiver
  does. Before, this came back as `QAR_STATUS_UNCLASSIFIED`, which made apps destroy and recreate
  their senders. A render sender's begin-frame does not report it: it waits through the pause.
- **C API:** `qar_session_get_graphics_device_id` (C# `Session.GetGraphicsDeviceId()`) returns
  the GPU adapter the session's devices were created on, as a chainable `QarGraphicsDeviceId`:
  the chained one, else the one QAROS selected, else the library's pick. Create your graphics
  device on it after onboarding. An app QAROS launches that chains no `QarGraphicsDeviceId` now
  gets its session on its target's GPU automatically; QAROS no longer sets `QAR_GPU_ADAPTER_ID`
  for it.
- **C API:** `qar_peer_spec_is_target_app` (C# `PeerSpec.IsTargetApp`) tells whether a peer is
  a target app: a headset, the Android streamer or a visualizer receiver. Find the targets to
  render for in the peer list with it and create a sender for each one you choose; the sender
  attaches its target to your app volume, which makes the target request your content.
  `qar_render_sender_subscribe_requests` cannot find targets for a new app: a target requests
  content only once it is attached.
- **C API:** `qar_session_request_onboarding_codes` (`QarRequestOnboardingCodesInit`: count,
  lifetime, optional planned peer id) mints a new set of one-time onboarding codes per call, for
  several devices to onboard at once; codes other callers hold and the hub's onboarding screen
  code stay valid. `qar_onboarding_invite_get_code` gives an invite's code text, which
  `QarOnboardCodeExt.code` accepts like a typed pairing code.
- **C#:** `Session.RequestOnboardingCodes(RequestOnboardingCodesOptions)` and
  `OnboardingInvite.GetCode()`, the same as the C API calls.
- **C API:** `qar-streaming-c` version `v0` (`qar_streaming_c/v0/api.h`), loaded at run time.
- **C#:** `Quaternar.Qaros` for `netstandard2.0`, `netstandard2.1` and `net8.0`, the C API as
  managed types in the `Quaternar.Qaros` namespace, returning `Result` instead of throwing.
- **C#:** wrappers for the rest of the v0 C API: OpenGL and Vulkan render-sender frames
  (`GetOpenGlFrame`, `GetVulkanFrame`), `RenderSender.TryBeginFrame`, app volume gesture modes, GUI
  panel gesture events, target-app invite/kill, `OnboardOptions.WithPeerId` / `WithGraphicsDevice`
  (`OnboardPeerId`, `GraphicsDeviceId`), `HandJoint`, and
  `StatusCode.RenderingProducerAppVolumeUnresolved`.
- **SDK:** `PeerSpec` version (`qar_peer_spec_get_version_id`, C# `PeerSpec.VersionId`) reports
  the product version the peer runs, for example `0.9.0`, `0.9.0-rc.1`, `0.9.0-dev.12+1a2b3c4d`,
  with `+demo` / `.demo` build metadata for a demo build. It was always `0.1.0`.
- **SDK:** every media-stream receiver reports two new timing components for its route, about
  every 0.5 s: `MediaStreamMetricComponent::ReceiverFrameAge` (frame creation to received; a
  rendering sender stamps creation when the app ends the frame) and `ReceiverPoseAge` (pose sample
  to received). Read them from `MediaStreamReceiverMetrics::FrameAge` / `PoseAge`; each carries the
  full distribution (count, mean, variance, min, max, jitter). Ages across machines are as exact as
  their clock sync.
- **SDK:** every video sender reports `MediaStreamMetricComponent::SenderFrameHold` (the app's
  acquire to return of a frame) about every 0.5 s, and a rendering sender also
  `SenderRenderRequestWait` (the acquired frame's wait for the receiver's render request). Read
  them from `MediaStreamMetrics::SenderFrameHold` / `SenderRenderRequestWait`.
- **Docs:** C# API reference (the `Quaternar.Qaros` namespaces) under **C# API** on the
  documentation site, generated from the binding's XML doc comments next to the C API reference.
  The landing page groups the types by area, with the entry points first.
- **Docs:** the documentation is versioned: each release keeps its own guides, diagrams and API reference,
  chosen in the navbar's version dropdown; the unreleased version is under `/next/`.

### Changed

- **Visualizer:** Source Applications shows "Streams to" of a QAROS API app as "Chosen by the
  app" instead of a locked "All target applications". The app itself decides which target apps
  it renders for: one, some or all of them.
- **Visualizer:** the visualizer opens only once it has joined the Hub's session. If it cannot,
  or does not within 60 s, it stays closed and the tray shows why (see Added). It no longer opens
  on panels that are still connecting.
- **Runtime:** the Hub's log files roll over and are deleted when old. The live file keeps its name
  (`launcher_stdout.log`, `<name>_stdout.log`, the tray's `qar-runtime-launcher_*.log`). Once it is a
  day old or 256 MB, it is renamed to `<name>.<UTC time>.log` and a new one starts. The oldest of
  these are deleted so each log file and its rolled-over copies stay under 3 GB. Copy the
  rolled-over files too when you collect logs.
- **Runtime:** an installed Hub (runtime ZIP or installer) writes its logs to
  `%TEMP%\quaternar\logs` instead of the data root: the tray's under `qaros-hub-service`, the
  launcher's and every process it starts under `qar-launcher-default\<session-id>`. A launcher crash
  dump goes to `qaros-hub-service\crashes`. `logFolder` still overrides the launcher's folder. A
  launcher restart moves the previous run's logs and dumps into `previous-runs\<UTC time>` of that
  folder instead of deleting them; the newest three runs are kept.
- **Visualizer:** an installed visualizer keeps its window layout (`imgui.ini`, stereo display
  layout) under `<data root>\streaming-viz\ui` with its other settings, instead of
  `%APPDATA%\QuaternAR\QAROS Hub`. A layout saved there is not carried over: arrange the
  panels once.
- **Runtime:** release builds of the visualizer, camera sources and the Monado runtime no longer
  run Khronos validation checks when Vulkan Configurator forces the validation layer on, and log a
  warning that it was forced. For latency or GPU measurements on a development machine, switch it
  off with `utils/Set-VulkanValidation.ps1 -Off` and back on with `-On`.
- **C API:** `qar_result_has_code()` also matches the codes of the causes a result wraps, as
  `qar::Result` equality does. A begin-frame on a reconnecting stream fails with
  `QAR_STATUS_RENDERING_PRODUCER_UNABLE_TO_DO_BEGIN_FRAME` and now matches
  `QAR_STATUS_MEDIA_STREAMING_STREAM_IS_RECONNECTING` too. `QarResult.code` is unchanged.
- **SDK:** the log file `QarLibraryInit.log_folder_path` enables (`qar_streaming.log`) rolls over:
  once it is a day old or 256 MiB, it is renamed to `qar_streaming.<UTC time>.log` and a new one
  starts. The oldest of these are deleted so the log takes at most 3 GiB. A long-running app's
  log no longer grows until the disk is full; read the rolled-over files for older lines.
- **SDK:** an invite from `qar_session_request_onboarding_invite` (C#
  `Session.RequestOnboardingInvite`) is no longer also made the code the hub's onboarding screen
  shows; the screen keeps its own code. The invite works as before.
- **SDK:** media-stream timing metrics no longer create a register version: a report no longer
  raises `MediaStream::UpdateCount` and is no longer stored. Metrics still arrive on media-stream
  updates and reads, at most one report window late. Do not use `UpdateCount` to detect a new
  metrics window; compare the component's `WindowIndex` or `Revision`.
- **SDK:** the order of `QarRenderSenderInit::frame_views` (C# `RenderSenderOptions.FrameViews`)
  is guaranteed: `qar_render_sender_layout` and every frame list their views in exactly the
  declared order, with textures in the order the views first use them. The sender used to return
  colour left, colour right, depth left, depth right whatever was declared; code that relied on that
  fixed order must follow its own declaration instead.
- **SDK:** a release build no longer runs Khronos validation checks on its own Vulkan instance
  when Vulkan Configurator forces `VK_LAYER_KHRONOS_validation` on for every process; the layer is
  told to check nothing for that instance only, and your application's own instances keep their
  validation. A warning in the log says the layer was forced. Debug and RelWithDebInfo builds are
  unchanged.

### Fixed

- **Packaging:** the runtime ZIP and the installer keep the GStreamer plug-ins in
  `bin\gstreamer-1.0` again. Installed flat in `bin`, every QAROS process loaded every DLL there
  while looking for plug-ins and logged about a hundred `BLACKLISTED plugin` errors at start. The
  runtime now only ever looks in `gstreamer-1.0` beside it: a copy of the runtime must keep that
  folder, or no plug-in loads.
- **Visualizer:** removing a receiver that never connected (the X on its card) no longer crashes
  the visualizer.
- **Visualizer:** (Demo) the Stream Graph offers one receiver at a time, the number the demo
  runs. The Add receiver card says so instead of adding a second receiver that never connects,
  and a receiver restored beyond it says why it does not connect. Remove the other receiver to
  watch it.
- **Runtime:** the Hub's launcher no longer crashes with heap corruption while a receiver it does
  not serve keeps asking for its stream.
- **Visualizer:** symbols and emoji in names and labels render instead of `?`. Windows uses
  Segoe UI, Segoe UI Symbol and colour Segoe UI Emoji; Linux uses system Noto/DejaVu fonts when
  installed. The GUI text font changes from the built-in bitmap font to Segoe UI.
- **Mixer:** emoji in display names render as single-colour outlines instead of `?` (Windows).
- **Mixer:** a mixer whose target has paused its stream (hidden display) keeps its source apps'
  streams up, paused, and still asks a newly placed app for its stream. Resuming the target
  resumes every source at once, without renegotiating; the Stream Graph shows the paused link.
- **Runtime:** a launcher that keeps crashing is restarted with growing delays again, not every
  second.
- **Visualizer:** the Vulkan cube launched from Source Applications shows on its targets. It now
  finds the target apps in the session itself; before, it waited for requests that no target
  could send.
- **Runtime:** the Hub, the visualizer and every QAROS process work under a Windows user name,
  data folder or install folder with non-ASCII characters (`C:\Users\Lukáš Jelínek`). Before, the
  Hub could not write its launcher config there and paths turned into `?`.
- **Mixer:** the StereoKit mixer and StereoKit source apps stop cleanly when the runtime stops
  them, instead of aborting or running until force-killed.
- **Mixer:** the StereoKit mixer no longer crashes when a source application stops and its app
  volume closes.
- **Mixer:** the StereoKit mixer starts on a GPU without `VK_GOOGLE_hlsl_functionality1` or
  `VK_KHR_format_feature_flags2`; it needs only external memory, timeline semaphores and
  descriptor indexing, whose non-uniform image indexing it now enables.
- **Runtime:** OpenXR launch learns a target GPU identity that arrives after pipeline adoption.
- **Runtime:** the Monado OpenXR runtime no longer draws an unused compositor frame on every
  refresh. While no viewer requests frames it uses no GPU, and it no longer reports
  `VUID-vkQueueSubmit-pSignalSemaphores-00067` under validation.
- **Runtime:** `sessionEndpoints` in the launcher config accepts the `"tcp/<host>:<port>"` form the
  bundled config shows, as well as `{"Protocol", "Hostname", "Port"}` objects. A malformed entry
  stops the launcher with a message instead of throwing.
- **Runtime:** the QAROS Hub tray reads a commented launcher config (`.jsonc`) and, started with no
  config path, the `qar-runtime-launcher.jsonc` beside the launcher. A config it cannot parse is
  reported instead of silently starting the hub on defaults.
- **Runtime:** the bundled Test OpenXR application draws the test camera's synthetic scene as a
  diorama filling its app volume, with a blue box at the volume's centre. Its cube sat 1.5 m in
  front of the volume, almost always outside the viewer's view, so its source reached the mixer as
  background only. Other OpenXR applications place content relative to `LOCAL`, which is the app
  volume's centre.
- **Visualizer:** a visualizer without saved settings starts in Basic mode. Importing the old
  `streaming_viz_settings.json` no longer carries its Debug unlock over, so Debug always needs its
  password; panel visibility is still imported.
- **C API:** `qar_streaming.h` compiles without warnings at `/W4` (MSVC C4098): the generated
  wrappers of `void` functions (`qar_runtime_destroy`, the `*_handle_destroy` family,
  `qar_result_log_if_error`, ...) no longer `return` a `void` expression, which strict C11 also
  rejects.
- **SDK:** destroying a session (`qar_session_handle_destroy`) could crash the process shortly
  afterwards with an access violation on a library thread, when a video or render sender was
  finishing a stream-state update at that moment. A sender destroyed after its session no longer
  reaches the session's media-stream register.
- **SDK:** a video receiver still waiting for a sender kept running after its session was
  destroyed, and one still pending when the process exited could crash it at exit inside the GPU
  driver. Destroying the session now ends it: the creation completes with
  `SessCancellationRequested` (status code 200). Cancelling the wait stops the creation before the
  call completes.
- **SDK:** a connected video receiver whose sender went away and which was still reconnecting when
  its session was destroyed could crash the process: the reconnect attempt kept asking through the
  destroyed session. Destroying the session now ends the attempt, and the receiver then reports
  `MediaStreamingStreamIsClosed` instead of reconnecting until its `ReconnectTimeout`.
- **SDK:** right after a GUI panel's visible-to list changed, listing the panels
  (`qar_query_gui_panels`, C# `GuiPanels.GetAll`) could return it with stream content and no
  stream, so reading its content failed with an `Unclassified` error without a message and C#
  `GetAll` failed altogether. Panels are now listed whole. An empty visible-to list means the
  panel is visible to every peer, so removing its last peer shows it to everyone; hide a panel
  through its state.
- **C API:** `QarGuiPanelInit::visible_to_peers` is no longer ignored: `qar_gui_panels_get_or_create`
  creates the panel visible only to those peers (empty: to every peer). A count without a pointer
  is rejected with `QAR_STATUS_LOGIC_ERROR`.
- **C#:** `GuiPanels.GetAll`, `AppVolumes.GetAll` and `Peers.GetAll` make one native query instead
  of a count and a query, so each returns in about half the time and no longer misses items added
  between the two calls.
- **SDK:** in a session without TLS, two peers occasionally never linked to each other, so what
  one published (GUI panel gestures, for example) never reached the other although each listed
  the other as a peer. Such sessions now connect and listen over TCP only and no longer use UDP;
  a firewall rule for them needs the TCP port alone. TLS sessions (QUIC) are unchanged.
- **SDK:** cancelling a subscription (disposing a C# subscription, cancelling its
  `QarCancelToken`) while an update was being delivered could end the process with a pure virtual
  call. Subscriptions now stop cleanly.
- **SDK:** leaving a session while `RenderingStreamReceiver().ConnectToStream` still waits for its
  stream no longer crashes the process. The pending connect now ends with
  `SessCancellationRequested` when its session goes away.
- **SDK:** every path the C API takes or returns as `const char*` (such as
  `QarLibraryInit.log_folder_path`) is UTF-8, in any host process. Before, the library read and
  wrote them in the Windows ANSI code page, so a folder under a user name like `Lukáš Jelínek`
  could not be used, and logged paths showed `?`. `qar_library_load` and
  `qar_transfer_library_load` take a UTF-8 path too, and C# progress messages are decoded as UTF-8
  instead of ANSI. Processes the SDK starts get their path, working folder, arguments and
  environment intact, in any host process, including paths with spaces.
- **SDK:** Peer snapshots now advertise the GPU adapter identity so the Hub can launch
  OpenXR sources on the correct GPU. Older snapshots retain an unknown adapter until refreshed.
- **SDK:** a video sender whose media-stream record the register closed (its receiver
  stopped) now closes itself instead of reporting a pause forever. The begin-frame call returns
  `QAR_STATUS_RENDERING_PRODUCER_STREAM_IS_CLOSED`; set up a new sender as on any closed stream.
- **SDK:** an application hosted by `qar-executable-service` stops gracefully when its parent
  closes its stdin pipe, even with unread bytes left in it, instead of running until
  force-killed.
- **SDK:** a render sender in a relaunched application takes its stream back within about 2 s of
  the previous process stopping or crashing, instead of being refused for up to a minute with "A
  different live sender peer already owns this media stream's video state".
- **SDK:** a new render sender no longer holds up the session's other senders for 2 s when it first
  publishes, which made a lock-step target drop the source as stalled right after it connected.
- **Docs:** the `onboarding_and_rejoin.c` example forgets the sibling peer it onboarded when run
  with forget: it kept a shadowed, empty onboarding id and could not remove the pairing.

### Security

- **Runtime:** a blacklisted (revoked) device is dropped by every launcher that has received the
  hub's revocation list: its pipeline stops at once and it gets none again until it re-pairs. A
  peer that has not received the list keeps accepting the device until its certificate expires (at
  most 24 h); a missing list never blocks anyone.
